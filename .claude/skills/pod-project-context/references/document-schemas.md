# Document Schemas

These are the canonical markdown schemas generated by `pod-project-context`
from `docs/_context-map.yaml`.

## Global rules

- Use verified, project-local content only.
- Keep `_context-map.yaml` paths workspace-relative and canonical.
- In markdown docs, render any path under the selected primary worktree as
  `<repo_root>/...` for readability.
- Define the alias once in a scope section when a markdown file contains
  repo-root paths:
  `<repo_root> = projects/<project_key>/<project_key>__primary_worktree`
- Keep paths outside the project root, such as `workspace.yaml`,
  workspace-relative.
- Remove sections that do not apply.
- If data is missing, add a short `Gap note:` rather than guessing.
- Keep index files shorter than their leaf files.
- `_context-map.yaml` stays canonical; optional lookup maps are related artifacts
  and should be referenced, not duplicated inside markdown narratives.

## `docs/architecture.md`

Required structure:

```markdown
# Architecture — <project name>

## Scope
- Project: `<project_key>`
- Workspace file: `workspace.yaml`
- Repo root: `<repo_root> = <workspace-relative-primary-worktree-path>`

## Architectural style
<Style name plus one short rationale paragraph.>

## Component map
<ASCII or Mermaid diagram using real repo names and `<repo_root>` paths where
applicable.>

## Components and responsibilities
| Component | Path | Responsibility |
|-----------|------|----------------|

## Dependency directions
- <Allowed or forbidden dependency with rationale.>

## Data flows
1. <Step 1>
2. <Step 2>

## External integrations
| Integration | Purpose | Entry point |
|-------------|---------|-------------|

## Decision notes
### <Decision title>
<Why this decision exists or why the gap remains.>

## Gaps
- <Only unresolved project-local gaps.>
```

Must exclude:

- file naming conventions
- generic coding standards
- leaf-pattern summaries
- full rule catalogs from `rules/*.md`
- exhaustive feature inventories
- route/page/screen catalogs
- lookup-map ownership tables

## `docs/pattern.md`

This file is the pattern index and must be written after all `patterns/*.md`
files are finalized.

Required structure:

```markdown
# Pattern Index — <project name>

Always read `docs/patterns/general.md` first.

## Naming strategy
<general-only|concept|layer|service|technology|combined and why>

## `docs/patterns/<filename>.md`
**Applies to:** <specific scope and `<repo_root>` paths>
**Contains:**
- <project-specific topic>
- <project-specific topic>
**When to read:** <concrete trigger>
**Related rules:**
- `docs/rules/<filename>.md`
```

Must exclude:

- long-form pattern walkthroughs
- architecture rationale paragraphs
- copied rule statements from `rules/*.md`

## `docs/patterns/*.md`

Always create `docs/patterns/general.md`. Create additional files only when the
project warrants them.

Required structure:

```markdown
# <scope name> patterns — <project name>

## Applies to
<What this scope covers and which `<repo_root>` paths are included.>

## Scope alias
`<repo_root> = <workspace-relative-primary-worktree-path>`

## Paths
- `<repo_root>/...`

## Observed shape
- <Recurring structure or flow found in code.>

## Naming and organization
- <File or module naming rules observed in this scope.>

## Common variations
- <How the pattern changes across this project, if it does.>

## Change triggers
- <When an agent should read this file before editing.>

## Related rules
- `docs/rules/<scope name>.md`

## Evidence
- `<repo_root>/...` — <what this file proves>
```

Must exclude:

- full architecture overview
- exhaustive rule lists
- generic advice not tied to project evidence

## `docs/rules.md`

This file intentionally indexes `docs/patterns/*.md` categories, not
`docs/rules/*.md`.

Required structure:

```markdown
# Rules Index — <project name>

Read this file after `docs/pattern.md` when the task needs enforceable
constraints.

## `docs/patterns/<filename>.md`
**Category:** <scope name>
**Applies to:** <what this pattern category covers using `<repo_root>` paths when relevant>
**Rule files:**
- `docs/rules/general.md`
- `docs/rules/<scope name>.md`
**Critical constraints:**
- <high-signal constraint summary>
- <high-signal constraint summary>
**When to read:** <concrete trigger>
```

Must exclude:

- full rule tables
- long pattern summaries
- architecture diagrams

## `docs/rules/*.md`

Always create `docs/rules/general.md`. Create additional files only when the
project has scope-specific constraints worth separating.

Required structure:

```markdown
# <scope name> rules — <project name>

## Scope
<What this rule file governs and which pattern categories it serves. Use
`<repo_root>` paths when project files are referenced.>

## Scope alias
`<repo_root> = <workspace-relative-primary-worktree-path>`

## Priority
- `must-not`
- `must`
- `should-not`
- `should`

## Rules
| ID | Level | Rule | Rationale | Exceptions |
|----|-------|------|-----------|------------|

## Related patterns
- `docs/patterns/<scope name>.md`

## Evidence
- `<repo_root>/...` — <what this file proves>

## Gaps
- <Only unresolved project-local gaps.>
```

Must exclude:

- component maps and architecture narrative
- detailed pattern walkthroughs
- generic repo policy that is not supported by project evidence
